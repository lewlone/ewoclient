# Rewo — the from-scratch native Minecraft client (cross-cutting rules)

A from-scratch Rust Minecraft: Java Edition client speaking the vanilla
protocol (pin: **26.2 / protocol 776**, read from the bundled jar's
`version.json`), rendered with **raw Vulkan via `ash`**. The priorities are
frame-time consistency (1%/0.1% lows) and input latency. It plugs into the
launcher as a `Native` instance and is **not** a JVM/mod project, so none of the
`ewo-jni`/mixin machinery applies. Keep `ewo-*` crates untouched in Rewo work.

4. Subsystem plans: `REWO_AUDIO_PLAN.md`, `REWO_VELVET_UI_PLAN.md` (a visual

## Verification (user mandate: headless-first)

The user does not manually test what a machine can check. Every milestone ships
a self-check path.

- Serverless `*shot --check` gates (validation layers ON, 0 VUIDs, fail-closed),
  run by `tools/gates.py`, whose `EXPECTED_GATES` pins the set: a new gate is
  added there in the same commit. Every GPU gate fails if validation is not
  active, and most pin an exact witness count. `mobshot --check` after any mob
  or UV change; demo PNG hash must stay byte-identical unless the change is
  meant to move it.
- **`rewo live --render-check`** (via `tools/render_check.py`) is the only
  check that drives the **windowed** client. Run it after any milestone that
  adds a render path. Validation is `cfg!(debug_assertions)`-gated for `live`,
  so run a **debug** build. M86 found nine features that had never rendered in
  the windowed client while every headless gate was green. A **tail** runs
  after the timed 8 s (`RENDER_CHECK_TAIL_SECONDS` caps it at 20 s): r83's
  bed, r84-r86's donkey and inventory, r87's boat, r88's horse, r89's camel (with r82's
  sprint state: a rider sprints only on a camel) and r90's nautilus live there (the cap is
  30 s; the run ends when they are done), because a sleeping player is
  immobile and every timed slot already holds a screen or a key. Witnesses
  that click an entity check what the production pick hit first (r71's item
  frame and r72's horse each took a click meant for something else).
  `REWO_PRECMD` is split on `;`: NBT's `[I;...]` int array cannot go in it
  (r90's nautilus owner is a UUID string). `/data get` of a PASSENGER's `Pos`
  is `(vehicle.x, own y, vehicle.z)` (`Entity.saveWithoutId`); r91 reads a
  rider's live position through a marker summoned `at @s`. A tail witness that changes the
  bot's state (an effect, a position) can leak into a run-wide maximum
  (r58's icon count is the timed run's since r90's Breath of the Nautilus).
  r53's waterlogged slab floods the spawn: a block a witness removes near it
  can turn straight to water (r78's flake, M224), so grade "gone", not "air".
  A witness that keeps the first sighting of a shared value (r20's panel)
  must start looking after its own staging, not at the run's start.
  `REWO_RC_CAPTURE_AT=<fraction>` and `REWO_RC_CAPTURE_MOUNT` (gates knobs)
  save one F2 capture into the staged game directory for a person to look at
  (`render_check.py --keep`); a capture found M220's preview bug.
- **`tools/load_check.py`** loads normal (not flat) terrain at render distance
  16 against a fresh server and fails on a column count other than the
  server's tracking set, a deferred column, or a validation message. Run it
  after touching the terrain arena, the mesher's output size, or what the
  client tells the server (M205 and M206 were both found by it). Not in
  `gates.py`: it needs a 3 GB server and minutes of world generation.
  `--light` runs the play bot there instead (CORRECTIONS 0 and
  `--light-check`); run it after touching light tables or physics.
- `tools/gates.py`, `tools/render_check.py` and `tools/load_check.py` take a machine-wide lock
  (`tools/gpu_lock.py`) so two GPU verifications never overlap: the
  self-hosted CI runner shares this desktop. A CI render check once read 65/66
  while another worktree's ran beside it.
- Before starting a test server, probe the port: a server that failed to bind
  still lets injected witnesses pass. The vanilla server stops on stdin EOF, so
  don't background it with `nohup … &`.
- `CORRECTIONS 0` from `rewo play` proves only the paths the harness exercises
  (flat walk). Knockback, riding and explosions need their own witnesses.

## Traps that recur across the whole client

- **Witnesses are wrong more often than code.** A fixture that sits where two
  candidate readings agree, a control that changes with its subject, and a
  pixel detector that counts against a painted background have each passed
  while measuring nothing. Derive the expectation from an independent source
  (decompile literals, jar PNG texels), never from the constant under test.
- **A gate that reimplements a slice of the app's setup misses what the app
  adds later** (`install_shapes`, `init_entities`). **A gate that supplies an
  input production must derive leaves the derivation untested** (M92's
  `mob_effect` ids). Call the production helper.
- **`PlaySession` owns a socket**, so its tests are `play/tests.rs` and the
  scripted-server integration tests in `rewo-net/tests/reconfigure.rs`. Still
  put logic in free, tested functions behind a thin adapter (M71, M97). Same
  for `LiveApp` (`live_cmd/tests.rs` tests the free functions).
- **Light follows vanilla's storage rules** (`rewo-world/src/chunk.rs`): the
  `light_update` empty masks zero a section (sky: a stored zero layer; block:
  no array), a `light_update` can only raise `sky_full_above`, an unstored sky
  section below the top reads the row above (`fill_sky_gaps`), and
  `Column::set_light` compares against the *effective* value. The
  incremental-vs-full property test covers a 2x2 column border and sparse sky.
- **`EntityTable` side maps are cleared in one place.** `remove` and `add`
  both call `clear_side_state`, which destructures every field of the table
  (no `..`), so a new per-entity map must be classified there and in the test's
  `side_rows`. A re-add is a removal then an add (vanilla's `addEntity` runs
  `removeEntity` first), so a reused id inherits no armour, anger clock or beam.
- **The local player is not in `EntityTable`.** Metadata and attributes
  addressed to it are dropped unless routed separately (M55, M73, M141e).
- **A vehicle the local player steers is the client's** (M221,
  `isLocalInstanceAuthoritative`): the session simulates it
  (`rewo_world::boat`), places it with `EntityState::set_simulated`, and
  server move packets for it only advance `SteeredBoat::server_base`; a
  server `move_vehicle` or teleport snaps it and is answered. A horse (M222)
  runs the player physics with its own `physics::Body` through
  `tick_ridden`; the render check's injected horse is held still with
  `movement_speed` 0 for that reason. A vehicle moves on the rider's
  PREVIOUS tick and, for a mount, on its modified `xxa` / `zza`
  (`rider_move_vector`, ×0.98), not on the raw keys (M226). Speeds a witness
  calls "vanilla's" must come from the decompile's chain, not a derivation
  the code shares: the server replays a steered vehicle's moves and cannot
  catch a wrong speed.
- **A right-click is `startUseItem`'s loop** (M229, `live_cmd/app.rs`
  `use_plan`): per hand, `use_item_on` for the block (always sent), then on
  a local PASS `use_item` (always sent); the local results come from
  `rewo_world::click_use`, one rule per overriding class
  (`tools/gen_click_use.py` names the class; a new override in a later
  version fails `every_override_class_was_reviewed`). Err toward ending the
  click: a wrongly-passed one sends a second packet the server acts on.
  The crosshair clips the ray against OUTLINE shapes (M230,
  `PlaySession::target_shape`, `BakedAssets::outline`), not collision: a
  button, a flower or a lever is targetable, water and air are not.
- **A container's player part is the player's inventory** in vanilla (one
  shared `Inventory`); Rewo keeps the player's menu apart, so
  `PlaySession::mirror_open_container_inventory` copies an open container's
  last 36 slots back every tick and before any close (M232). Anything that
  reads the player inventory while a container is open sees it a tick late.
- **A menu whose `quick_move()` is `Unimplemented` cannot be clicked at
  all**: `slot_kind` is `None`, every click is "not predictable" and is
  never sent (`click_screen`). The enchanting table was unusable that way
  until M236 and the brewing stand until M237. A new menu needs its arm.
- **The render-check server's seed is random** (`level-seed=` empty) and the
  harness stages `generate-structures=false` (M236): a village once put the
  spawn on a roof and two dozen witnesses failed with it. It also stages
  `gamerule spawn_monsters false`: `spawn-monsters=false` no longer stops
  slimes, which killed the survival bot mid-tail. The use tail logs each
  stage's position and health (`render-check: use stage`).
- **The frame's FOV is vanilla's dynamic FOV** (M233,
  `PlaySession::fov_degrees`, `rewo_world::fov`): the option times the
  eased `getFieldOfViewModifier` (sprint, speed, flying, a drawn bow, the
  spyglass) and water at the eye. The render-check bot carries Speed I, so
  its standing FOV is 77, not 70: never project a witness with a constant.
- **One accessor per concept.** When two call sites each compute "which menu",
  "which origin" or "which conversion", they drift (M89, M106b, M112, M151).
- **The M-numbers aren't a contiguous index** (M52, M61, M64, M66, M68 each
  name two pieces of work). Use commit subjects.
- **"Class-C blocker" claims are often wrong**: the data is frequently in the
  client jar rather than on the wire (furnace recipes, merchant quick-move,
  stonecutter list, smithing sets). Check the jar before believing one.
- Market-leader client mods (Sodium, EntityCulling, Xaero's, JourneyMap, Jade,
  WTHIT) are non-open-source. **Don't read their source as reference.**
- Public servers are out of scope (ban risk). Staging is the user's Frogsy network.
- **`cargo fmt` is enforced** (CI `fmt` job; `rustfmt.toml` pins LF; the
  generated modules are `#[rustfmt::skip]`). Claim render-check witness ids (`rNN`) and atlas
  rows in §0.0's allocation table **before** writing code, and check the code
  too (`grep -oE '"r[0-9]+ ' crates/rewo-app/src/live_cmd/render_check.rs`):
  the 2026-09 play-test fix took r65 that M179 had claimed in the table.
  Parallel branches once minted the same id, and git merges that silently.
- Write new files as LF bytes. PowerShell `Add-Content` appends CRLF.

## Build features and test knobs

- **`--features gates`** (rewo-app; enables `rewo-gpu/gates` and
  `rewo-mesh/oracle`) compiles the gate subcommands, `live --render-check`,
  `play`, and every `REWO_*` test knob. Without it the knobs read as unset
  whatever the environment says (`rewo-app/src/knobs.rs`,
  `rewo-gpu/src/knobs.rs`): that includes `REWO_FOG`, `REWO_MOB_DEBUG_TEX`,
  `REWO_CEM_NOANIM` and `REWO_NO_SYNC_VALIDATION`. Read a new knob through
  `knobs::var`, never `std::env::var`.
- **`live_cmd/render_check.rs`, its witness blocks and the injected-state
  fields are `#[cfg(feature = "gates")]`**, not merely refused at runtime: a
  byte search of the default-features `rewo.exe` finds none of the witness
  strings, and the scripted packet injections are not in it. Anything
  production needs (`wavy_cape_requested`, `validate_unit`) lives in
  `live_cmd/mod.rs`. `--render-check` still exists and errors without the
  feature.
- **Pin what a graded comparison counted, not just that frames came back.**
  `rewo-app/src/probes.rs` (`PROBES.bad(..)`) counts each comparison as it is
  evaluated; `skyshot`, `lightmapshot` and `tintshot` pin that count beside
  the frame count, so a section that renders but stops comparing fails.
  `leashshot` records every witness unconditionally and compares against
  `EXPECTED_WITNESSES` with `!=`. `tools/numbers.py` shows the pins.
- **Game directory.** `options.txt` is `<game dir>/options.txt`, written
  atomically. `rewo-app/src/game_dir.rs` resolves the directory once: `rewo
  live --game-dir DIR`, then the launcher's `REWO_GAME_DIR`, then the current
  directory (standalone runs). Never open `options.txt` by a bare relative path.
  `tools/render_check.py` stages its own game directory (with an `options.txt`
  holding r73's `renderDistance`) inside the server's scratch folder.
- **Tracy** runs only with `--features profile`; the default build's
  `tracy_client` calls are no-ops (no profiler thread, no LAN broadcast).
- The shipped client sends no test packets: the first-spawn dirt stack is
  `REWO_GIVE_DIRT` (a gates knob that `tools/render_check.py` sets, because
  the render-check baseline was calibrated with it).
- CI's `test` job and `gates.yml` both run `cargo test --workspace
  --features rewo-app/gates`; the `shipped` job builds the default features.

## Mutation batteries

The per-milestone `m*_mutate.py` scripts are archived in
`tools/history/mutations/`; new batteries use the shared harness
`tools/mutate_lib.py` (its default build includes `--features gates`).

- Grade by the `test result:` line or the gate's exit code. **Exit code alone
  can't tell a failing test from a failing build**, and a substring can
  mis-decode (Windows locale mangled an em dash into "every verdict KILLED").
- Every battery carries a **no-op control that must SURVIVE**. A battery run
  against an already-red command reads KILLED for everything.
- **After a battery, the exe is the last mutant.** Restore fixes sources, not
  binaries, so rebuild before any post-battery gate run.
- A killed or timed-out battery skips its `finally` and **leaves the mutation on
  disk**. Grep for the markers first. A hung test binary can hold the link
  output (linker error 1104).
- Never run git operations while a battery is modifying files.
- A survivor is a question: an equivalent mutant (prove it), a weak fixture, or
  logic in an untestable place.
